# Phase 5 — State layer (Riverpod)

**Status:** completed

Build the Riverpod state layer that wires the Phase 3 math and Phase 4 location layer to
the (future) UI, with a correct once-per-second clock tick, a once-per-day sunrise
recompute, lifecycle handling, and global error handlers. This is the plan for Phase 5 of
[../docs/implementation_plan.md](../docs/implementation_plan.md).

**Read first:** [../CLAUDE.md](../CLAUDE.md) · architecture §5, §6, §8, §10, §12 ·
implementation plan Phase 5.

---

## The issue (what is missing)

Phases 1–4 gave us pure services and models:

- `SolarCalculator.resolveDay(now, lat, lon)` → a `SolarDay` (anchor sunrise + span,
  with safe fallbacks).
- `TimeCalculator.toDharmaTime(now, sunrise, span)` → a `DharmaTime`.
- `LocationService` (live GPS), `LocationRepository` (saved location + use-live flag),
  `LocationResolver.resolve(...)` (live → saved → none).

But nothing yet **drives** them. There is no ticking clock value, no provider for the
active location or display settings, no lifecycle handling, and `main()` has no global
error handlers. `core_providers.dart` only declares the two root injection providers
(`sharedPreferencesProvider`, `appConfigProvider`), which `main.dart` already overrides.

Phase 5 fills this gap so Phase 6 (the clock screen) can just `watch` providers.

---

## Design decisions

1. **Clock output type — `ClockSnapshot`.** The plan text says "a tick provider producing
   `DharmaTime`". A bare `DharmaTime` is not quite enough for the readout: the UI must also
   show the *ticking civil time*, whether we fell back to a polar/midnight day, and whether
   the anchor came from live or saved location. So the tick produces a small immutable
   `ClockSnapshot { civilTime, dharma, isPolar, source }`. `dharma` is still a `DharmaTime`,
   so this is a superset of the plan, not a departure from it. (Minor, noted as a deviation.)

2. **Once-per-day sunrise recompute.** The clock notifier caches the resolved `SolarDay`
   and only calls `SolarCalculator.resolveDay` again when `now` crosses the cached day's end
   (the next sunrise) — not every tick. This satisfies architecture §19 ("recompute
   sunrises once per day, not every tick") and the day-boundary roll.

3. **Injectable clock for testing.** A `nowProvider` exposes a `DateTime Function()`
   (default `DateTime.now`). The notifier reads time only through it, so tests can feed a
   fixed instant and assert the snapshot without real timers.

4. **No-location fallback.** When `effectiveLocationProvider` is `null` (no live fix and no
   saved location), the notifier uses a **midnight-anchored** day (`startOfDay` UTC, fixed
   86,400 s span) built inline — the same shape `SolarCalculator` uses for its polar
   fallback. This keeps CLAUDE.md hard rule 4 (never crash on a missing anchor) without
   adding a public method to the Phase 3 service.

5. **Lifecycle via `AppLifecycleListener`.** The notifier owns an `AppLifecycleListener`
   (Flutter ≥ 3.13, we are on 3.41): stop the 1 s timer on `pause`/`hide`, and on
   `resume`/`show` recompute immediately (catches a date change while paused) and restart
   the timer. The timer and the listener are cancelled in `ref.onDispose`.

6. **Global error handlers use `debugPrint`, not a new package.** Adding a `logger`
   dependency is out of scope for Phase 5 and risks the offline/dep rules. `main()` will set
   `FlutterError.onError` and `PlatformDispatcher.instance.onError` to present/log and
   swallow so the app does not hard-crash; verbose detail is gated behind
   `AppFlavorConfig.enableVerboseLogging`. Coordinates are never logged.

## Provider dependency shape

```
clockProvider (ClockSnapshot, ticks 1/s)
  ├─ nowProvider (DateTime Function())
  ├─ solarCalculatorProvider
  ├─ timeCalculatorProvider
  └─ effectiveLocationProvider (EffectiveLocation?)
        └─ locationProvider (LocationState)
              └─ locationRepositoryProvider ─ sharedPreferencesProvider
              └─ locationServiceProvider

displayModeProvider (DisplayMode)
  └─ sharedPreferencesProvider
```

Direction stays `providers → services/repositories → shared_preferences/models`
(architecture §9). No provider imports a screen, `BuildContext`, or a route.
